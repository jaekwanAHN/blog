경험을 토대로 AI를 활용하여 작성한 글 입니다.

배포된 `chuksung.vercel.app`에 처음 들어가면 느리다는 얘기를 들었다. 그런데 `pnpm perf`로 재는 Lighthouse 점수는 96~99다. 원장은 건강한데 체감은 10초대라는 게 말이 안 돼서, **실제 태스크가 화면에 뜨기까지**를 종점으로 잡고 모바일 조건에서 다시 쟀다.

결론부터: 서버는 빠르다. 느린 것은 **브라우저가 JS를 다 받아 실행할 때까지 데이터를 요청조차 못 하는 구조**다.

측정 조건은 이랬다.

```
대상   production / 인증 상태
조건   모바일 390×844 · 4G 1.6Mbps/150ms · CPU 4×
계정   perf (태스크 9,573건)
커밋   cc973d3
```

## 워밍 상태의 시간 예산

"실제 태스크 표시"를 종점으로 잡은 데는 이유가 있다. Lighthouse가 재는 LCP는 이 종점이 아니다 — `/daily`의 서버 HTML에는 **"불러오는 중…" 문구만** 들어 있어서, LCP는 로딩 문구가 뜨는 시점을 재고 끝난다.

문서 요청부터 태스크 표시까지 **3,191ms**. 구간별로 쪼개면 이렇다.

| 구간 | 소요 | 비중 | 비고 |
|---|---:|---:|---|
| 문서 | 436ms | 13.7% | TTFB 219ms |
| **JS 전송·파싱·실행** | **2,345ms** | **73.5%** | **← 병목** |
| 데이터 왕복 | 243ms | 7.6% | `/api/tasks` |
| 렌더 | 167ms | 5.2% | |

첫 API 요청이 나가는 시각이 **2,781ms**다. 그 전까지 앱은 무엇도 물어보지 못한다. 서버 응답(219ms)도, DB 조회(243ms)도 병목이 아니다. **병목은 그 사이에 놓인 JS 부트스트랩 한 덩어리**다.

## 그 2.3초는 전송인가 연산인가

같은 2.3초라도 "다운로드가 느린 것"과 "실행이 느린 것"은 대책이 완전히 다르다. 그래서 망 제한과 CPU 제한을 하나씩 걷어내고 같은 종점을 다시 쟀다. 각 3회의 중앙값이다.

| 조건 | FCP | 첫 API 요청 | 콘텐츠 | 기준 대비 |
|---|---:|---:|---:|---:|
| 4G + CPU 4× *(기준)* | 1,372 | 2,784 | 3,225 | — |
| 빠른 망 + CPU 4× *(망 제거)* | 544 | 1,079 | 1,411 | −1,814 |
| 4G + CPU 1× *(CPU 제거)* | 1,496 | 2,503 | 2,716 | −509 |
| 빠른 망 + CPU 1× *(둘 다 제거)* | 584 | 716 | 910 | −2,315 |

망을 걷어내면 **1.8초**가 사라지고, CPU를 걷어내면 **0.5초**가 사라진다. 즉 이 문제는 **연산량이 아니라 전송량**이다.

검산도 맞는다. 361KB를 1.6Mbps로 내려받으면 산술적으로 **1.76초** — 관측된 1.81초와 사실상 일치한다.

## 그 361KB의 내역

`/daily` 초기 로드는 전송 361KB / 압축 해제 1.07MB, 실제 요청된 청크는 15개다.

| 덩어리 | 전송 | 해제 | 브라우저에서 하는 일 |
|---|---:|---:|---|
| react-dom | 71KB | 222KB | 하이드레이션 — 필수 |
| **@supabase/supabase-js** | **57KB** | **216KB** | **인증 3곳에만 쓰임** · realtime·postgrest·storage 전량 미사용 |
| Next.js 런타임 · 라우터 | 69KB | 253KB | RSC·내비게이션 — 필수 |
| **Geist + Geist Mono (woff2)** | **52KB** | **52KB** | **둘 다 preload** · Mono는 헤더 시계·타이머에만 |
| 앱 코드 · react-query · CSS | 112KB | 327KB | 페이지·훅·스타일 |

브라우저 Supabase 클라이언트가 실제로 쓰이는 곳은 셋뿐이다 — `LoginButton`의 OAuth 시작, `useAuth`의 `getUser()`, `Header`의 로그아웃. `.from()`·`.rpc()`·`.channel()` 호출은 클라이언트 코드에 **한 건도 없다**. 그런데 realtime 웹소켓 스택까지 포함한 216KB가 대시보드 전 페이지에 실린다.

## 여기에 콜드스타트가 얹힌다

지금까지는 전부 워밍 상태의 숫자다. 그런데 20분간 사이트를 전혀 건드리지 않은 뒤 첫 요청을 재보면 다른 그림이 나온다. 개인 프로젝트의 실제 트래픽에서는 **대부분의 "첫 접근"이 이 상태**다.

| 지점 | 콜드 | 워밍 | 차이 |
|---|---:|---:|---:|
| 비인증 `/` → 307 | 824 | 285 | +539 |
| 문서 TTFB | 596 | 219 | +377 |
| FCP (로딩 셸) | 1,632 | — | — |
| **태스크 표시** | **2,682** | **950** | **+1,732** |

무스로틀 유선에서 **+1.7초**다. 여기에 위의 모바일 조건이 겹치면 2.3초(JS) + 1.7초(콜드) + 문서·데이터 왕복이 쌓여 **보고된 10초대에 도달한다**. 중저가 단말이면 JS 구간이 더 늘어난다.

> **왜 전부 콜드 함수를 타는가**
>
> 빌드 출력의 모든 라우트가 `ƒ (Dynamic)`이다. 루트 레이아웃이 테마 쿠키를 읽으려 `await cookies()`를 호출하기 때문이고, 이 트레이드오프는 [하이드레이션 불일치를 다룬 글](/blog/2026-08-05-hydration-mismatch-streaming-query)의 사례 2에 이미 기록돼 있다. 당시 판단("실질 변화는 `/_not-found` 뿐")은 맞았지만, **정적 라우트가 하나도 없다는 것은 CDN에서 나가는 응답이 하나도 없다**는 뜻이기도 하다 — 비로그인 방문자가 보는 `/login`조차 함수 기동을 기다린다.

## 개선안 — 측정된 지렛대 순

순번은 측정된 절감폭 순서다. `코드`는 지금 구조 안에서 되는 것, `구조`는 설계 결정을 다시 여는 것.

### 1. 태스크를 서버에서 렌더한다 — 약 −1.8초 · 구조

지금은 1.06MB의 JS가 전부 도착·실행돼야 비로소 `/api/tasks`를 *요청*한다. `/daily`를 서버 컴포넌트로 돌려 태스크를 HTML에 실어 보내면, 데이터 왕복 243ms가 사라지는 것을 넘어 **콘텐츠가 FCP(1.37초)에 도착**한다. JS는 그 뒤에 붙어 상호작용만 얹는다.

걸림돌은 "유효 오늘"이 클라이언트 타임존 + `day_start_time`에 달려 있어 서버가 날짜를 못 정한다는 점이다. 테마 쿠키와 같은 방식으로 `tz` 쿠키를 심거나(`profiles.timezone` 컬럼도 대안) 해결된다 — 첫 방문 한 번만 현재 경로로 폴백.

대상: `app/(dashboard)/daily`, 쿠키 또는 스키마 1열.

### 2. 대시보드에서 브라우저 Supabase 클라이언트를 뺀다 — 약 −450ms · 코드

`useAuth`가 브라우저에서 `getUser()`를 부르는데, 그 값은 **레이아웃이 이미 서버에서 알고 있다**. 사용자 정보를 서버에서 내려주면 대시보드 번들에서 supabase-js를 통째로 걷어낼 수 있다 — 전송 57KB(≈280ms)와 브라우저 → Supabase Auth 왕복 167ms가 함께 사라진다. 로그인 페이지에는 OAuth 때문에 남긴다.

대상: `hooks/auth/useAuth.ts`, `layout/Header.tsx`.

### 3. Geist Mono의 preload를 끈다 — 약 −145ms · 코드

Mono는 헤더 시계와 타이머 페이지에만 쓰이는데 29KB가 모든 페이지의 크리티컬 패스에서 preload된다. `preload: false`면 필요한 화면에서만 늦게 받는다.

대상: `app/layout.tsx`.

### 4. 콜드스타트를 줄인다 — 약 −1.7초 중 일부 · 구조

가장 큰 단일 항목이지만 Hobby 플랜의 구조적 제약이다. 코드로 손댈 수 있는 부분은 **정적화** — 테마를 쿠키 대신 인라인 스크립트로 주입하면 루트 레이아웃의 `cookies()`가 빠지고 `/login`이 CDN 정적 응답이 된다. 다만 이는 하이드레이션 글 사례 2의 결론을 되돌리는 일이라, FOUC 재발 위험과 함께 따로 판단할 사안이다. 프록시(`sin1`)와 함수(`icn1`)의 리전 분열은 [프록시 리전을 다룬 글](/blog/2026-08-11-proxy-local-jwt-verification-getclaims)에 적어둔 대로 플랜 한계다.

### 5. 잔가지 — 합쳐서 약 −300ms · 코드

차단 A/B로 재보니 개별 효과가 작아 단독으로는 착수할 근거가 약하다.

- `TemplateManager`가 닫혀 있어도 `/api/task-templates`를 부른다 (−171ms, `open`일 때만 `enabled`).
- 사이드바가 8개 라우트를 15건으로 프리페치한다 (−294ms). 다만 프리페치는 *이후* 내비게이션을 위한 장치라 끄는 것보다 `loading.tsx`를 두어 프리페치가 멈출 경계를 만드는 편이 낫다. 현재 저장소에는 `loading.tsx`·`error.tsx`가 한 개도 없다.

## 왜 원장은 Perf 96~99인데 체감은 10초인가

`pnpm perf`는 **로컬 빌드를 로컬 Chromium으로** 잰다. 콜드스타트도, 사용자↔함수 거리도, 실제 회선도 그 안에 없다. 이 한계는 리전 글에 이미 적혀 있다.

여기에 한 겹이 더 있다. **Lighthouse의 LCP가 재는 대상이 "불러오는 중…" 텍스트다.** 태스크가 언제 뜨는지는 어느 지표에도 잡히지 않는다. 그래서 원장이 건강해 보이는 동안에도 체감은 얼마든지 나빠질 수 있다.

> **이슈 #110의 우선순위를 올릴 근거**
>
> "배포 URL에 Lighthouse를 돌릴 수 없다"는 현재 `priority: low`로 열려 있다. 이번 분석에서 **배포 URL에 Lighthouse를 붙이는 것 자체는 기존 `scripts/perf/auth.mjs` 재사용으로 어렵지 않게 됐다**. 다만 진짜 필요한 지표는 LCP가 아니라 **실제 콘텐츠 표시 시각**이므로, #110은 도구 문제가 아니라 *종점 정의* 문제로 다시 쓰는 편이 맞다.

## 재보고 접은 가설

측정 전에 유력해 보였지만 데이터가 부정한 것들. 다시 꺼내지 않도록 남긴다.

- **✕ 하이드레이션 게이트가 데이터 요청을 직렬화한다** — `useHydrated` 게이트가 `/api/tasks`를 늦춘다고 봤다. 실제 측정에서 레이아웃 쿼리와 페이지 쿼리의 발사 간격은 **0~2ms**다. 둘 다 부트가 끝난 뒤 동시에 나간다.
- **✕ RSC 프리페치 15건이 주범이다** — 전량 차단해도 −294ms로, 기준값의 회차 간 편차(3,188~3,664ms)와 겹친다.
- **✕ 서버나 DB가 느리다** — 워밍 상태에서 문서 TTFB 219ms, API 왕복 100~250ms, 문서 스트림은 220ms 안에 닫힌다. `tasks` 인덱스도 `(user, scope, target_date)`로 걸려 있다.
- **✕ 템플릿 시딩 RPC가 그날의 첫 접근을 붙잡는다** — 시간 게이트를 통과한 `/api/tasks` 한 번 안에 포함되며, 그 요청 전체가 243ms다.
- **✕ 로컬 `pnpm dev`의 온디맨드 컴파일이다** — Turbopack Ready in 303ms, 첫 요청 500ms, 이후 41ms. 해당 없음.

## 재현 방법

이번 측정은 저장소에 없는 일회성 스크립트로 했다. 계속 쓸 값이면 `scripts/perf/`에 들여야 하고, 그건 #110과 함께 판단할 일이다. 핵심은 종점을 **DOM에 태스크가 나타난 시각**으로 잡는 것이다.

```js
// 종점: LCP가 아니라 실제 콘텐츠
await page.goto(BASE + '/', { waitUntil: 'commit' })
await page.waitForFunction(() =>
  document.body.innerText.includes('오늘의 태스크') ||
  document.body.innerText.includes('태스크가 없')
)

// 조건: Lighthouse 모바일과 같은 스로틀
cdp.send('Network.emulateNetworkConditions',
  { downloadThroughput: 1638400/8, latency: 150 })
cdp.send('Emulation.setCPUThrottlingRate', { rate: 4 })

// 인증: 기존 헬퍼 재사용
import { getAuthCookies, toBrowserCookies } from './scripts/perf/auth.mjs'
```

콜드 측정은 **20분간 배포 URL에 아무 요청도 보내지 않은 뒤** 한 번만 재야 한다. 측정 중 다른 요청이 섞이면 함수가 워밍되어 값이 무의미해진다 — 첫 시도가 그렇게 오염됐다.

---

이번에도 결론은 "재보기 전엔 모른다"였다. 리전 글에서는 무료 플랜을 의심했다가 함수 위치가 범인이었고, 이번에는 DB와 하이드레이션 게이트를 의심했다가 둘 다 데이터가 부정했다.

가장 오래 남은 건 계측 쪽이다. Perf 96~99라는 숫자는 거짓말을 한 게 아니라 **다른 것을 재고 있었다.** 서버 HTML에 "불러오는 중…"만 담아 보내는 순간, LCP는 로딩 문구가 뜨는 시점을 재고 끝난다. 지표가 초록불인데 체감이 나쁘면, 지표가 틀린 게 아니라 **종점을 잘못 잡은 것**일 수 있다.
