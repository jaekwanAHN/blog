경험을 토대로 AI를 활용하여 작성한 글 입니다.

취업 준비 플래너 앱의 PR 두 개가 CI에서 넘어가지 않았다. 하나는 문서·툴링 추가, 하나는 안 쓰는 환경변수 제거. 둘 다 코드 로직을 건드리지 않는 변경이라 막힐 이유가 없어 보였다.

```
in_progress  CI  chore/claude-tooling-commands-skills  2h10m49s
pending      CI  chore/remove-dead-env-vars            1h13m48s
```

`lint-and-build`는 둘 다 초록불인데 `e2e`에서 멈춰 있었다. `e2e`는 required check라 이 상태로는 어느 쪽도 머지되지 않는다.

## 한쪽은 멈췄고, 한쪽은 기다리고 있었다

두 PR의 상태가 서로 다르다는 게 첫 단서였다.

```
#58  e2e: in_progress   08:45:46 시작
#126 e2e: pending       08:46:06 부터 대기
```

`pending`은 무언가를 기다리는 상태다. 기다리는 대상은 뻔했다 — 먼저 돌고 있는 `#58`의 e2e. 그러니 진짜 조사 대상은 `#126`이 아니라 `#58`이었다. 스텝을 열어봤다.

```
5. Install dependencies        [completed]
6. Install Playwright browsers [in_progress]   ← 08:46:01 부터
7. Run E2E tests               [pending]
```

`pnpm exec playwright install --with-deps chromium`에서 멈춰 있었다. 이게 얼마나 비정상인지 보려고 직전에 성공한 run의 같은 스텝을 봤다. **1분 02초.** 73배를 넘겼으니 "느린" 게 아니라 "멈춘" 것이라고 판단했다.

(이 판단은 맞았지만, 비교 대상으로 고른 1분 02초는 나중에 보니 그 자체가 이미 이상치였다. 이 얘기는 뒤에서 다시 한다.)

## 진행 중인 job은 로그를 안 준다

원인을 보려고 로그를 뽑으려 했는데 여기서 막혔다.

```bash
$ gh api repos/…/actions/jobs/95996407735/logs
(진행 중 job 은 로그 API 미제공)
```

GitHub Actions는 **완료된 job의 로그만** API로 내려준다. 웹 UI의 실시간 스트림은 별개 경로다. 즉 멈춘 job을 진단하려면 **일단 죽여야 한다.** 진단하려면 증거를 없애는 행동을 먼저 해야 하는, 좀 이상한 상황이다.

다행히 취소는 로그를 지우지 않는다. 취소된 job도 그 시점까지의 로그는 남는다. 취소 전에 스텝별 타임스탬프만 따로 받아두고 죽였다.

```bash
$ gh run cancel 32229594643
✓ Request to cancel workflow 32229594643 submitted.
```

그리고 취소가 완료되자마자 벌어진 일이 인과를 확정해줬다.

```
10:06:58Z  #58=in_progress          #126.e2e=pending
10:07:29Z  #58=completed/cancelled  #126.e2e=in_progress   ← 즉시 시작
```

`#58`이 죽은 지 몇십 초 만에 `#126`의 e2e가 시작됐다. `#126`은 고장난 적이 없었다. 그냥 줄을 서 있었다.

## 로그가 말한 것

취소된 job에서 로그를 받아 꼬리를 봤다. 범인이 그대로 적혀 있었다.

```
08:46:33Z  Ign:5 http://azure.archive.ubuntu.com/ubuntu noble-security InRelease
08:46:34Z  Ign:2 http://azure.archive.ubuntu.com/ubuntu noble InRelease
08:46:36Z  Ign:3 http://azure.archive.ubuntu.com/ubuntu noble-updates InRelease
           … azure 미러 전 항목 Ign 반복 …
08:46:40Z  Hit:2 https://archive.ubuntu.com/ubuntu noble InRelease
08:46:40Z  Get:3 https://archive.ubuntu.com/ubuntu noble-updates InRelease [126 kB]
08:46:40Z  Get:4 https://archive.ubuntu.com/ubuntu noble-backports InRelease [126 kB]
08:46:40Z  Get:5 https://archive.ubuntu.com/ubuntu noble-security InRelease [126 kB]

           ← 여기서 1시간 20분 14초 동안 출력 없음

10:06:54Z  ##[error]The operation was canceled.
```

순서대로 읽으면 이렇다.

1. GitHub 호스티드 러너는 Azure 위에 있어서 `azure.archive.ubuntu.com`이라는 로컬 미러를 쓴다. 그런데 **전 항목이 `Ign:`** — 응답하지 않았다.
2. apt가 공용 미러 `archive.ubuntu.com`으로 폴백했다. 여기까지도 이미 열화된 경로다.
3. InRelease 파일 4개 중 3개를 받고 **4번째에서 커넥션이 정지**했다.
4. 그리고 끝. 에러도, 재시도도, 타임아웃도 없이 1시간 20분.

핵심은 4번이다. apt는 **끊긴 연결**은 처리하지만 **멈춘 연결**에는 기본 타임아웃이 없다. TCP 연결은 살아 있고 데이터만 안 오는 상태에서, apt는 영원히 기다린다.

그리고 이 apt를 부른 건 우리가 아니다. `playwright install`의 `--with-deps` 플래그가 브라우저 실행에 필요한 시스템 라이브러리를 깔려고 내부적으로 `apt-get`을 호출한다. 우리 코드도, 두 PR의 변경사항도 원인이 아니었다.

## 왜 PR 하나의 문제가 전부를 막았나

여기서부터가 진짜 배운 부분이다. 외부 미러가 가끔 멈추는 건 우리가 어쩔 수 없다. 문제는 **그 하나가 저장소 전체를 세웠다**는 것이다.

이 앱의 e2e는 이렇게 직렬화돼 있다.

```yaml
  e2e:
    concurrency:
      group: e2e-shared-account   # PR·브랜치와 무관하게 고정
      cancel-in-progress: false
      queue: max
```

이유가 있다. e2e가 단일 공유 테스트 계정의 실 DB를 조작하기 때문에, 두 PR의 테스트가 동시에 돌면 서로의 시딩·설정·목록을 밟는다. 그래서 프로세스 안에서는 `workers: 1`로, 러너를 가로질러서는 이 concurrency 그룹으로 묶어 한 번에 하나만 돌게 했다.

`queue: max`는 2026년 5월에 추가된 옵션이다. 기본값은 pending을 **하나만** 두고 나머지를 취소해서, PR 3개가 몰리면 가운데 것이 실행도 못 해보고 cancelled로 죽는다. required check가 cancelled면 머지가 막히니, 취소 대신 FIFO로 줄 세우려고 넣은 설정이다.

**이 설정은 옳고, 이번 장애의 원인이 아니다.** `#126`이 pending이었던 건 버그가 아니라 설계대로 기다린 것이다.

다만 직렬화는 조용히 전제를 하나 깔고 있었다 — **"실행 중인 job은 언젠가 끝난다."**

그 전제를 깬 게 두 번째 원인이다. `ci.yml`의 두 job 어디에도, 스텝 수준에도 `timeout-minutes`가 없었다. 그러면 GitHub 기본값인 **6시간**이 적용된다.

정리하면 이렇게 겹쳤다.

| 층 | 무엇 | 통제 |
|---|---|---|
| 1 | apt가 우분투 미러에서 정지 | 외부, 불가 |
| 2 | 상한이 없어 6시간까지 방치 | **우리 문제** |
| 3 | 직렬화가 1건의 장애를 전역으로 증폭 | 설계된 대가 |

병렬 CI였다면 PR 하나가 늦어지는 걸로 끝났을 일이다. 직렬 자원 위에서는 같은 사고가 **모든 PR의 머지 차단**이 된다. 수동으로 죽이지 않았다면 14:46까지, 그러니까 6시간 내내 물려 있었을 것이다.

## 해결

### 즉시

멈춘 run을 죽였다. 그게 전부다. 락이 풀리자 대기하던 e2e가 바로 시작됐고, 죽인 PR은 재실행해서 줄 뒤에 다시 세웠다.

### 상한을 걸자 — 그런데 몇 분으로?

원인은 알았으니 대책은 뻔해 보였다. 문제가 난 스텝에 상한을 걸면 된다.

```yaml
      - name: Install Playwright browsers
        timeout-minutes: 5          # 정상 1분 02초니까 5배 여유
        run: pnpm exec playwright install --with-deps chromium
```

여기서 잠깐 멈췄다. 5분이라는 숫자의 근거가 **표본 하나**였다. 직전 성공 run의 1분 02초. 그거 하나 보고 5배를 곱한 것이다.

그래서 최근 CI run 40건에서 이 스텝의 소요를 전부 뽑아봤다.

| 시각 (UTC) | 소요 | |
|---|---|---|
| 08-10 ~ 08-18 03:58 (12회) | **20~35초** | 안정 |
| 08-18 04:29 | 403초 (6분 43초) | 통과 |
| 08-19 04:41 | 352초 (5분 52초) | 통과 |
| 08-19 06:34 | 158초 (2분 38초) | 통과 |
| 08-19 07:09 | 62초 (1분 02초) | 통과 |
| 08-19 08:46 | **∞** | **이번 장애** |
| 08-19 10:07 | 22초 | 정상 |
| 08-19 10:11 | **1042초 (17분 22초)** | **통과** |

세 가지가 한꺼번에 무너졌다.

**첫째, 내가 "정상값"이라고 부른 1분 02초가 이미 이상치였다.** 진짜 기준선은 20~35초다. 하필 사고 직전 run을 골랐는데, 그게 이미 3배쯤 부푼 값이었다.

**둘째, 처음 발생이 아니었다.** 08-18 04:29에 403초가 있었다. 기준선의 12배다. 그런데 job이 **통과했기 때문에** 아무도 몰랐다. 그날 이후로 계속 조짐이 있었고, 이번에 무한대로 커진 것뿐이다.

**셋째, 그리고 이게 제일 중요한데 — 내 상한 5분은 성공한 run을 죽였을 값이다.** 맨 아래 1042초짜리는 다름 아닌 내가 재실행한 그 PR이고, 17분 22초를 걸려서 **통과했다.** job 전체로는 20분 35초. 그러니 job 상한 20분도 이 성공을 잘랐을 것이다.

게이트를 지키려고 건 상한이 게이트를 막는다. 하마터면 사고 대응한다고 사고를 하나 더 만들 뻔했다.

10:07에 22초, 4분 뒤 10:11에 1042초. **47배 차이다.** 점점 나빠지는 추세가 아니라, 러너가 어느 미러에 붙느냐에 따라 갈리는 간헐적 현상이었다.

### 순서를 바꿨다 — 분산을 없애고 나서 상한을 건다

분포가 이렇게 널뛰는 상태에서 상한부터 거는 건 순서가 틀렸다. 먼저 분산을 만드는 원인을 없애야 한다.

**1순위, apt에 직접 상한과 재시도.**

```yaml
      - name: apt 네트워크 상한
        run: |
          echo 'Acquire::http::Timeout "30";'  | sudo tee /etc/apt/apt.conf.d/99timeout
          echo 'Acquire::https::Timeout "30";' | sudo tee -a /etc/apt/apt.conf.d/99timeout
          echo 'Acquire::Retries "3";'         | sudo tee -a /etc/apt/apt.conf.d/99timeout
```

멈춘 커넥션을 30초에 끊고 3회 재시도한다. **정지(∞)와 지연(1042초)을 동시에 잡는 유일한 조치**다. 나머지는 전부 피해를 줄일 뿐 원인을 안 건드린다.

**2순위, Playwright 브라우저 캐시.** `cache: pnpm`은 걸어뒀는데 브라우저는 매 run 새로 받고 있었다. 직렬화된 게이트라 처리량이 곧 병목인데 매번 다운로드를 하고, **무엇보다 멈출 수 있는 창을 매 run 연다.**

여기엔 함정이 하나 있다. 캐시가 적중해도 `--with-deps`의 apt 경로는 남는다. 브라우저 바이너리는 캐시돼도 시스템 의존성 설치는 별개라, **정작 이번에 멈춘 지점이 그대로 살아 있을 수 있다.** 캐시만으로 끝났다고 보면 안 되는 이유고, 1순위가 따로 필요한 이유다.

**3순위, 그러고 나서 상한.** 1·2로 분산을 줄인 뒤 분포를 다시 떠서 값을 정한다. 지금 관측만으로 굳이 잡는다면 스텝 10분, e2e job 25분, lint-and-build 15분 정도다. 관측된 성공 최대치(20분 35초)보다는 위여야 한다.

핵심은 **6시간을 유한한 값으로 바꾸는 것**이지 정확한 숫자를 맞히는 게 아니다. 그리고 값을 내릴 때는 반드시 분포를 다시 뜬다.

## 예방 — 다음에 같은 걸 안 겪으려면

처음 겪는 종류의 장애라 조치보다 이쪽을 더 오래 생각했다.

**상한이 없는 단계의 상한은 0이 아니라 6시간이다.** `timeout-minutes`를 안 쓴 건 "제한을 두지 않겠다"는 선택처럼 느껴졌지만, 실제로는 "6시간을 허용하겠다"는 선택이었다. 기본값이 관대할수록 명시가 중요하다. 앞으로 CI에 새 job을 추가할 때 `timeout-minutes`를 `runs-on`과 한 세트로 쓰기로 했다.

**직렬 자원과 타임아웃은 한 쌍이다.** 공유 계정 때문에 e2e를 직렬화한 판단 자체는 지금도 옳다고 본다. 하지만 직렬화를 도입할 때 "그럼 하나가 안 끝나면?"을 같이 답했어야 했다. 자원을 독점시키는 설계를 넣는 순간, 그 독점을 강제로 끝낼 수단이 함께 들어가야 한다. 이번엔 그 한쪽만 있었다.

**외부 의존은 실패가 아니라 정지로 온다.** 네트워크 의존을 생각할 때 보통 "실패하면 어떻게 처리하지"를 준비한다. 그런데 이번 apt는 실패하지 않았다. 에러도 안 냈고 연결도 안 끊었다. 그냥 멈췄다. 에러 핸들링은 정지를 잡지 못한다. 정지를 잡는 건 타임아웃뿐이다.

**기준선은 표본 하나가 아니라 분포다.** "1시간 20분째 설치 중"만으로는 느린 건지 멈춘 건지 알 수 없어서 직전 성공 run과 비교했다. 그 판단 자체는 맞았지만, 하필 고른 그 표본이 이미 3배 부푼 값이었다. 표본 하나로 이상을 판정하면 우연히 맞고, 표본 하나로 **임계값을 정하면 틀린다.** 상한을 거는 것처럼 숫자를 확정해야 하는 순간에는 반드시 분포를 뜰 것.

**실패하지 않는 열화는 보이지 않는다.** 08-18에 이미 기준선의 12배가 찍혔는데 아무도 몰랐다. job이 초록불이었기 때문이다. CI는 통과/실패라는 이진 신호만 주고, 그 사이의 "통과했지만 12배 느려짐"은 아무 데도 알리지 않는다. 이번 장애는 하루 넘게 예고된 뒤에 온 것이고, 나는 그 예고를 볼 수단이 없었다. 임계값을 정하든 추이를 그리든, 초록불 안쪽을 보는 장치가 따로 있어야 한다.

**진단하려면 죽여야 하는 경우가 있다.** 멈춘 job의 로그를 API로 못 받는다는 건 이번에 처음 알았다. 죽이는 걸 망설이면 원인 모른 채로 시간만 간다. 대신 죽이기 전에 스텝별 타임스탬프처럼 API로 받을 수 있는 상태는 따로 저장해두면 된다. 실제로 이번에 취소 전 스냅샷을 남겨둔 게 타임라인 재구성에 그대로 쓰였다.

## 덤으로 나온 것들

취소된 job 로그를 끝까지 읽다가 별개 문제도 두 개 발견했다.

```
##[warning]Node.js 20 is deprecated. The following actions target Node.js 20
but are being forced to run on Node.js 24:
actions/checkout@v4, actions/setup-node@v4, pnpm/action-setup@v4
```

지금은 강제 승격으로 돌아가지만 언젠가 깨진다. 액션 메이저 버전을 올려야 한다.

그리고 이미 머지된 PR의 CI run 하나가 5시간 46분째 `queued`로 남아 있었다. 취소해보려 했더니 GitHub 자체가 못 했다.

```bash
$ gh run cancel 32215041445
HTTP 500: Failed to cancel workflow run

$ gh api -X POST .../force-cancel
HTTP 500: Failed to cancel workflow run
```

concurrency 그룹이 없는 `lint-and-build`까지 `queued`인 걸로 보아 대기열에 걸린 게 아니라 run 자체가 디스패치되지 않은 서버측 정지 상태였다. 실제로 나중에 생성된 job이 이걸 앞질러 실행됐으니 이번 봉쇄의 원인은 아니었다. 이런 것도 있구나 하고 넘겼다.

---

결론은 싱겁다. 코드에 버그가 없었고, CI 설정도 틀리지 않았다. 우분투 미러가 잠깐 멈췄을 뿐이다. 그런데 상한 한 줄이 없어서 그 잠깐이 1시간 20분이 됐고, 직렬화 설계 때문에 한 PR의 1시간 20분이 모든 PR의 1시간 20분이 됐다.

장애는 대개 하나의 큰 실수보다 이렇게 작은 것 몇 개가 겹쳐서 난다.

가장 오래 남은 건 따로 있다. 원인을 다 밝히고 대책까지 적고 나서, 마지막에 숫자 하나가 찜찜해서 분포를 떠봤을 뿐인데 — 처음 겪는 사고인 줄 알았던 게 하루 넘게 예고돼 있었고, 내가 적어둔 대책은 성공한 빌드를 죽일 값이었다. **원인 분석이 끝났다고 느낀 지점이 사실은 측정을 한 번 더 해야 할 지점이었다.**
