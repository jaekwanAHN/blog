풀이를 구현하기 전에 확인할 것은 세 가지다. **최대 입력에서 얼마나 계산하는가, 동시에 얼마나 저장하는가, 계산 결과를 정확하게 표현할 수 있는가.**

JavaScript에서는 `10^8회 = 1초`, `숫자 하나 = 메모리 8바이트`를 모든 상황에 적용하면 판단이 틀어질 수 있다. 아래에서는 경험적인 판단 기준과 정확한 저장 크기를 구분한다. 실행 환경은 Node.js를 가정한다.

## 1. O(n)은 초 단위가 아니다

시간복잡도는 입력이 커질 때 연산량이 증가하는 형태다. `O(n)`이라는 정보만으로 1초에 처리할 수 있는 `n`을 정할 수는 없다.

```js
// 둘 다 반복 횟수는 n이지만, 반복 한 번의 비용은 다르다.
function sumNumbers(n) {
  let sum = 0;
  for (let i = 0; i < n; i++) sum += i;
  return sum;
}

function makeRecords(n) {
  const records = [];
  for (let i = 0; i < n; i++) records.push({ id: i, label: String(i) });
  return records;
}
```

두 번째 코드는 객체와 문자열을 만들고 배열을 키운다. 숫자를 더하는 루프와 달리 메모리 할당과 가비지 컬렉션(GC)의 영향도 받는다. 엄밀히는 문자열 변환 비용도 자릿수에 따라 달라진다.

### 1초 제한을 만났을 때의 출발점

다음은 **벤치마크 결과나 통과 보장이 아닌, 풀이 후보를 고르기 위한 경험칙**이다. 숫자 비교·덧셈·배열 접근처럼 가벼운 작업을 기준으로 생각한다.

| 대략적인 핵심 작업 횟수 | 초기 판단 |
| --- | --- |
| `10^6` 이하 | 우선 검토할 만한 규모. 무거운 작업이 숨어 있는지 확인 |
| `10^7` 정도 | 가능한 후보지만 반복 내부 비용과 실제 시간을 확인 |
| `10^8` 정도 | 1초에 통과한다고 가정하지 않는다. 더 적은 연산의 풀이부터 검토 |
| `10^9` 이상 | 일반적인 짧은 제한에서는 연산량을 줄일 방법부터 찾기 |

고도로 최적화된 숫자 루프는 `10^8`회도 빠르게 끝날 수 있다. 반대로 문자열 처리나 `BigInt` 연산, 객체 생성은 훨씬 적은 반복에서도 부담이 된다. CPU, Node.js 버전, JIT 최적화, 입력 파싱, 채점 플랫폼의 언어별 시간 보정까지 달라지므로 고정된 초당 연산 수로 외우지 않는다.

### 입력 크기로 후보 복잡도 좁히기

| 최대 입력 크기 | 먼저 검토할 풀이 | 연산량을 볼 때의 주의점 |
| --- | --- | --- |
| `n ≤ 10` | 순열·백트래킹 | `10! = 3,628,800`, 각 상태의 추가 작업도 곱하기 |
| `n ≈ 20` | 부분집합·비트마스크 | `2^20 ≈ 105만`, `n × 2^n`이면 약 2,097만 |
| `n ≈ 100` | `O(n³)`도 후보 | `100³ = 100만` |
| `n ≈ 1,000` | `O(n²)`도 후보 | `1,000² = 100만` |
| `n ≈ 10,000` | 보통 `O(n log n)` 또는 `O(n)`부터 | `n² = 1억`이므로 이중 반복은 검증 필요 |
| `n ≈ 100,000` | `O(n log n)`, `O(n)` | `n log₂ n ≈ 166만`, `n² = 100억` |
| `n ≈ 1,000,000` | `O(n)` 중심, 정렬은 비용 확인 | `n log₂ n ≈ 1,993만`, 입력·메모리도 중요 |
| `n ≥ 10,000,000` | 선형 처리도 비용 점검 | 전체 저장 대신 순차 처리 가능한지 검토 |

표의 숫자는 증가율을 비교하는 계산이다. 정렬의 실제 비교 횟수나 실행 시간을 뜻하지 않는다. 시간 제한이 길거나 상태당 작업이 가벼우면 더 큰 입력도 가능하다.

입력에서 `n`이 실제 원소 수인지도 확인한다. `n × n` 격자는 원소가 `n²`개라서 한 번 훑어도 `O(n²)`다. 반면 “값의 상한이 `10^9`”라는 조건은 원소가 `10^9`개 있다는 뜻이 아니다.

테스트케이스가 여러 개라면 비용을 합산한다. 케이스별 `O(n²)`의 총비용은 `Σ nᵢ²`이고, `O(n log n)`은 `Σ nᵢ log nᵢ`다. 개별 최댓값뿐 아니라 전체 입력 크기 제한을 읽어야 한다.

## 2. 변수의 값 표현과 실제 메모리는 구분한다

| 종류 | 값 표현·범위 | 메모리 계산에서의 의미 |
| --- | --- | --- |
| `Number` | IEEE 754 배정밀도, 안전한 정수 범위는 `±(2^53 - 1)` | 값 형식은 64비트지만 변수·일반 배열 원소가 항상 8바이트인 것은 아님 |
| `BigInt` | 임의 정밀도 정수 | 자릿수와 엔진 구현에 따라 증가. 고정 8바이트가 아님 |
| `Boolean` | `true`, `false` | 일반 배열에서 원소당 1비트나 1바이트라고 가정하면 안 됨 |
| `String` | UTF-16 코드 단위의 시퀀스 | `length × 2`는 논리적인 코드 단위 크기. 실제 할당량과는 다를 수 있음 |
| `null`, `undefined` | 각각의 특별한 값 | 배열 칸을 차지하지 않는다는 뜻이 아님 |
| `Object`, `Array`, `Map`, `Set` | 참조를 통해 사용하는 자료구조 | 값 외에 참조·관리 정보·여유 용량 등 추가 비용 존재 |

`let`, `const`, `var`를 바꿔도 자료형의 저장 폭이 바뀌지 않는다. `const`는 재할당을 막는 선언이고 메모리를 압축하는 선언이 아니다. 값의 의미와 범위는 [ECMAScript 자료형 명세](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html)에서 확인할 수 있다.

V8은 일반 배열을 작은 정수, 실수, 일반 값 등 원소 종류에 따라 다르게 취급한다. 참조 크기 역시 포인터 압축 사용 여부에 영향을 받는다. 따라서 `Array(n).fill(0)`의 총크기를 언어 차원에서 확정할 수 없다. [V8 배열 원소 표현](https://v8.dev/blog/elements-kinds), [V8 포인터 압축](https://v8.dev/blog/pointer-compression)

밀집된 숫자 배열을 처음 가늠할 때는 **원소 저장 부분을 칸당 8바이트로 가정한 계산**이 출발점이 될 수 있다. 다만 이것은 일반 배열의 정확한 크기나 상한이 아니다. 배열 자체의 관리 비용, 행 배열, 여유 용량, 표현 변경 중의 추가 할당을 포함하지 않는다. 객체 배열은 이 계산으로 추정하지 않는다.

### 값의 최대 크기도 함께 계산하기

입력이 안전한 정수라고 중간 결과도 안전한 것은 아니다.

```js
console.log(Number.MAX_SAFE_INTEGER); // 9007199254740991
console.log(Number.isSafeInteger(1_000_000_000 * 1_000_000_000)); // false

// 큰 정수는 문자열에서 바로 변환한다.
const value = BigInt("9007199254740993");
console.log(String(value)); // "9007199254740993"
```

큰 정수를 먼저 `Number`로 읽으면 이미 정밀도를 잃을 수 있다. 입력값뿐 아니라 누적합, 거리 합, 곱셈의 최대치까지 계산한다. `(a * b) % mod`도 곱셈 단계에서 부정확해지면 나머지 연산으로 복구할 수 없다.

`BigInt`는 일반 산술에서 `Number`와 섞어 사용할 수 없으며, 자릿수가 커지면 연산 비용도 커진다. 큰 정수의 덧셈·곱셈을 무조건 `O(1)`로 세면 안 된다.

`Number`에 대한 비트 연산은 32비트 정수 변환이 개입한다. `1 << 31`은 음수가 되고 `1 << 32`는 1이므로, 큰 정수 계산에 비트 연산을 그대로 적용하지 않는다. 일반적인 양수 비트마스크를 쓸 때는 비트 수를 먼저 확인한다.

## 3. 정확한 저장 크기가 필요하면 TypedArray

`TypedArray`는 원소의 저장 형식과 바이트 수가 정해져 있다. 아래 크기는 **원소 데이터만의 크기**이며 뷰 객체와 버퍼 관리 비용은 별도다.

| 종류 | 원소당 크기 | 저장 범위·용도 |
| --- | ---: | --- |
| `Int8Array` | 1바이트 | `-128 ~ 127` |
| `Uint8Array` | 1바이트 | `0 ~ 255`, 방문 여부·작은 상태 |
| `Int16Array` | 2바이트 | `-32,768 ~ 32,767` |
| `Uint16Array` | 2바이트 | `0 ~ 65,535` |
| `Int32Array` | 4바이트 | `-2,147,483,648 ~ 2,147,483,647` |
| `Uint32Array` | 4바이트 | `0 ~ 4,294,967,295` |
| `Float32Array` | 4바이트 | 단정밀도 실수. 연속 정수 정확성은 `±2^24`까지 |
| `Float64Array` | 8바이트 | 배정밀도 실수. `Number`의 수치 표현 |
| `BigInt64Array` | 8바이트 | `-2^63 ~ 2^63 - 1` |
| `BigUint64Array` | 8바이트 | `0 ~ 2^64 - 1` |

크기와 형식은 [ECMAScript TypedArray 명세](https://tc39.es/ecma262/multipage/structured-data.html#table-the-typedarray-constructors)에 정의되어 있다. 생성 시 숫자형 원소는 0, BigInt형 원소는 `0n`으로 초기화된다.

```js
const visited = new Uint8Array(1_000_000);
const distances = new Int32Array(1_000_000);
distances.fill(-1);

console.log(visited.byteLength);   // 1000000
console.log(distances.byteLength); // 4000000
```

정수형 TypedArray에 범위를 넘는 값을 넣으면 예외로 알려주는 대신 해당 폭으로 변환된다. 예를 들어 `new Uint8Array([256])[0]`은 0이다. 거리나 DP 값의 최대치, 미방문 표시 `-1`을 저장할 수 있는지 확인한다. `Infinity`가 필요하면 정수형 대신 `Float64Array` 등을 사용한다.

`BigInt64Array`도 64비트로 제한된다. 일반 `BigInt`처럼 임의로 큰 값을 보존하는 배열이 아니다. 고정 길이로 생성한 TypedArray에는 일반 배열처럼 `push`할 수 없다는 점도 고려한다.

## 4. n × n 배열의 메모리 계산

```txt
원소 데이터 바이트 = 행 수 × 열 수 × 원소당 바이트
MiB = 바이트 / 1,048,576
```

아래는 평탄한 TypedArray 하나의 원소 데이터다. `1 MB = 1,000,000바이트`, `1 MiB = 1,048,576바이트`이며 표는 MiB를 사용한다. 채점 사이트의 제한 단위도 확인한다.

| 정사각형 한 변 n | 칸 수 | Uint8: 1바이트/칸 | Int32: 4바이트/칸 | Float64: 8바이트/칸 |
| --- | ---: | ---: | ---: | ---: |
| 1,000 | 100만 | 0.95 MiB | 3.81 MiB | 7.63 MiB |
| 2,000 | 400만 | 3.81 MiB | 15.26 MiB | 30.52 MiB |
| 3,000 | 900만 | 8.58 MiB | 34.33 MiB | 68.66 MiB |
| 5,000 | 2,500만 | 23.84 MiB | 95.37 MiB | 190.73 MiB |
| 10,000 | 1억 | 95.37 MiB | 381.47 MiB | 762.94 MiB |

다음 일반 배열은 각 행도 별도의 배열 객체이므로 위 표를 실제 총메모리로 그대로 적용할 수 없다.

```js
const n = 3;
const grid = Array.from({ length: n }, () => Array(n).fill(0));
```

평탄한 TypedArray를 쓰면 행별 객체를 없애고 원소 저장량을 예측할 수 있다.

```js
const rows = 3;
const cols = 4;
const grid = new Int32Array(rows * cols);

grid[1 * cols + 2] = 7; // grid[1][2]에 해당
console.log(grid[1 * cols + 2]); // 7
console.log(grid.byteLength); // 48
```

인덱스는 `row * cols + col`이다. 평탄화는 자료구조의 부가 비용을 줄이지만 저장해야 하는 칸 수 `O(rows × cols)`를 줄이지는 않는다.

### 메모리 제한 256 MiB라면 어디서 풀이를 바꿀까?

전체 제한을 배열 하나에 모두 배정할 수는 없다. Node.js 런타임, 입력, 출력, 큐, 임시 배열이 함께 존재한다. 예를 들어 다른 용도로 남길 공간을 고려해 **배열 하나의 예산을 128 MiB로 정했다면**, 다음 식을 쓸 수 있다. 128 MiB는 설명용 예산이며 환경마다 적절한 예산은 다르다.

```txt
n의 이론상 최대 = floor(sqrt(배열 예산 바이트 / 칸당 바이트))

128 MiB 예산:
1바이트/칸 → n = 11,585
4바이트/칸 → n = 5,792
8바이트/칸 → n = 4,096
```

이는 원소 데이터만으로 계산한 상한이다. 실전에서는 여유를 둬야 하며, 일반 배열에 대한 보장도 아니다.

- `n = 5,000`의 `Float64Array` 격자는 약 190.73 MiB다. 256 MiB 제한에서 다른 자료구조까지 필요하다면 전체 격자를 보관하는 방식을 재검토한다.
- 같은 크기의 `Int32Array` 격자는 약 95.37 MiB지만, 두 장이면 약 190.73 MiB다. 배열 개수를 곱해야 한다.
- `n = 10,000`은 방문 여부만 `Uint8Array`에 담아도 약 95.37 MiB다. 거리와 큐를 함께 만들면 훨씬 커진다.
- 메모리에 들어가도 한 번 순회하는 데 `n²`칸을 처리한다. 공간을 줄인 뒤에도 시간 제한을 따로 확인한다.

따라서 “2차원 배열은 n이 몇 이상이면 불가능하다”보다 **칸 수 × 칸당 크기 × 동시에 유지하는 배열 수**로 판단하는 편이 정확하다.

## 5. 메모리가 부족할 때 바꾸는 방법

| 상황 | 검토할 변경 | 비용 변화 |
| --- | --- | --- |
| DP에서 직전 행만 필요 | 한 행 또는 두 행만 유지 | 공간 `O(RC)` → `O(C)`, 시간은 그대로일 수 있음 |
| 방문 여부만 저장 | `Uint8Array`, 더 필요하면 비트셋 | 1바이트/칸 또는 약 1비트/칸 |
| 실제로 사용하는 좌표가 적음 | 필요한 상태만 Map에 저장 | 전체 격자 대신 방문 상태 수에 비례, 엔트리당 비용은 큼 |
| 정점은 많지만 간선은 적음 | 인접행렬 대신 인접리스트 | `O(V²)` → `O(V + E)` |
| 값은 크지만 서로 다른 값은 적음 | 좌표 압축 | 값의 최댓값 대신 서로 다른 값 개수만큼 저장 |
| 이전 입력을 다시 볼 필요가 없음 | 순차 처리·누적 계산 | 전체 원소 보관 생략 |

좌표 압축은 순서·동등성만 중요할 때 유용하다. 실제 거리나 좌표 간 간격이 필요한 문제라면 그 정보도 따로 보존해야 한다. 희소 상태용 `Map`은 모든 칸을 넣으면 밀집된 TypedArray보다 비싸질 수 있다.

한 행만 저장하는 DP 예시로 두 문자열의 최장 공통 부분 수열(LCS) 길이를 구할 수 있다. 현재 칸에는 이전 행의 같은 열, 현재 행의 이전 열, 이전 행의 이전 열만 필요하다.

```js
function lcsLength(a, b) {
  if (a.length < b.length) [a, b] = [b, a];
  const dp = new Uint32Array(b.length + 1);

  for (let i = 1; i <= a.length; i++) {
    let diagonal = 0;
    for (let j = 1; j <= b.length; j++) {
      const above = dp[j];
      dp[j] = a[i - 1] === b[j - 1]
        ? diagonal + 1
        : Math.max(above, dp[j - 1]);
      diagonal = above;
    }
  }

  return dp[b.length];
}

console.log(lcsLength("ACAYKP", "CAPCAK")); // 4
```

영문자처럼 인덱스로 한 문자씩 접근할 수 있는 입력을 가정한다. 시간은 `O(|a| × |b|)`지만 추가 공간은 `O(min(|a|, |b|))`다. 실제 수열을 복원하려면 별도의 전략이 필요하다. 공간을 줄일 때 어떤 정보를 버리는지 확인해야 한다.

## 6. JavaScript에서 놓치기 쉬운 비용

아래는 일반적인 밀집 배열과 통상적인 구현을 기준으로 한 분석이다. 엔진의 특수 최적화를 통과 근거로 삼지는 않는다.

| 코드·기능 | 고려할 비용 | 풀이에서의 대응 |
| --- | --- | --- |
| `push`, `pop` | 일반 동적 배열에서 끝 삽입은 분할 상환 `O(1)`, 끝 삭제는 보통 `O(1)` | 스택에 활용, 확장 시 추가 할당은 고려 |
| `shift`, `unshift`, 앞쪽 `splice` | 많은 원소의 인덱스 변경 가능 | 큰 BFS 큐에는 head 인덱스 사용 |
| `includes`, `indexOf` | 원소 수에 비례하는 선형 탐색 | 반복 조회는 Set 또는 범위 기반 배열 검토 |
| `slice`, `[...arr]`, `map`, `filter` | 순회와 결과 배열 생성 | 반복문 안에서 큰 배열을 계속 복사하지 않기 |
| `sort` | 보통 `O(n log n)`으로 예산 추정, 비교 함수 비용·작업 공간 추가 | 숫자는 `(a, b) => a - b`, 원본 변경도 확인 |
| `Map`, `Set` | 통상 평균 `O(1)` 조회로 분석하지만 해싱·저장 비용 존재 | 긴 문자열 키 생성 비용도 포함 |
| `BigInt` 연산 | 피연산자의 비트 수에 따라 비용 증가 | 일반 숫자 연산과 같은 상수 비용으로 보지 않기 |
| 깊은 재귀 | 호출 스택 누적 | 깊이가 큰 DFS는 명시적 스택 검토 |

ECMAScript는 `sort`에 특정 정렬 구현·시간복잡도를 강제하지 않는다. `Map`도 평균적으로 원소 수에 대해 선형보다 빠른 접근을 요구할 뿐, 모든 연산의 최악 `O(1)`을 보장하지 않는다. [배열 메서드 명세](https://tc39.es/ecma262/multipage/indexed-collections.html), [Map 명세](https://tc39.es/ecma262/multipage/keyed-collections.html#sec-map-objects)

### BFS에서는 큐와 좌표도 메모리를 쓴다

```js
const queue = [0];
let head = 0;

while (head < queue.length) {
  const current = queue[head++];
  // 이웃을 처음 발견하면 방문 표시 후 queue.push(next)를 수행한다.
}
```

head 방식은 앞부분 삭제를 피하지만 처리한 칸도 배열에 남는다. 위 방식은 큐의 최대 동시 길이뿐 아니라 **누적 삽입 수**에 비례하는 저장 공간을 사용한다. 객체를 넣었다면 참조도 남으므로 필요에 따라 처리한 참조를 비우거나 원형 큐를 쓴다. 참조를 비워도 배열의 용량 자체가 바로 줄어들지는 않는다.

격자 좌표 `[r, c]`를 매번 새 배열로 만드는 대신 `r * cols + c`라는 정수 하나로 저장하면 작은 배열 객체를 대량 생성하는 비용을 줄일 수 있다. 복원은 `Math.floor(id / cols)`, `id % cols`로 한다.

예를 들어 `5,000 × 5,000` 격자에서 방문 상태 1바이트, 거리 4바이트, 각 칸을 한 번 넣는 고정 큐 4바이트를 모두 할당하면 원소 데이터만 `25,000,000 × 9`, 약 **214.58 MiB**다. 원본 격자와 런타임은 아직 포함하지 않은 수치다.

### 입력·출력과 순간 최대 메모리

```js
const numbers = input.trim().split(/\s+/).map(Number);
```

이 코드는 짧지만 큰 입력에서는 원본 문자열, 토큰 배열과 문자열들, 숫자 배열이 한동안 함께 존재할 수 있다. 파싱 비용도 입력 길이에 비례한다. 입력이 크면 인덱스로 숫자를 읽는 파서나 `Buffer` 기반 파서를 검토한다. 전체 입력을 한 번 읽는 방식이라면 토큰 배열을 없애도 입력 자체의 저장 공간은 남는다.

반복적인 `console.log` 대신 출력을 모아 쓰면 호출 비용을 줄일 수 있지만, 출력 배열과 `join` 결과 문자열의 메모리를 계산해야 한다. 출력이 매우 크면 적당한 크기로 나눠 쓴다.

`Math.max(...largeArray)`는 큰 배열을 함수 인자로 펼치므로 인자 개수 한계에 걸릴 수 있다. 큰 데이터의 최댓값은 루프로 구한다. 재귀 깊이와 인자 개수의 안전 한계는 환경마다 달라 특정 숫자를 외우지 않는다.

메모리 제한은 마지막에 남는 자료구조만으로 판단하지 않는다. 배열 복사, 정렬, 파싱 중의 임시 데이터와 GC가 실행되기 전의 객체까지 포함한 **순간 최대 사용량**이 중요하다.

## 7. 로컬에서 확인하는 방법

알고리즘 후보를 고른 다음 최대 입력에 가까운 사례로 확인한다. 아래 코드는 측정 API의 사용 예시이며 채점 속도를 예측하는 벤치마크는 아니다.

```js
const { performance } = require("node:perf_hooks");

const before = process.memoryUsage();
const start = performance.now();

const n = 1_000_000;
const values = new Int32Array(n);
let checksum = 0;
for (let i = 0; i < n; i++) {
  values[i] = i;
  checksum += values[i];
}

const elapsedMs = performance.now() - start;
const after = process.memoryUsage();
const toMiB = (bytes) => (bytes / 1024 / 1024).toFixed(2);

console.error({
  node: process.version,
  elapsedMs,
  checksum,
  dataBytes: values.byteLength,
  rssMiB: toMiB(after.rss),
  heapUsedMiB: toMiB(after.heapUsed),
  arrayBuffersMiB: toMiB(after.arrayBuffers),
  rssDeltaMiB: toMiB(after.rss - before.rss),
});
```

`performance.now()`는 밀리초 단위 경과 시간 측정에 사용할 수 있다. 전체 풀이를 평가하려면 입력 파싱과 출력 생성도 측정 범위에 포함한다. [Node.js 성능 측정 문서](https://nodejs.org/api/perf_hooks.html#performancenow)

`process.memoryUsage()`의 값은 바이트 단위다.

- `rss`: 코드와 런타임 등을 포함해 프로세스가 실제 메모리에 올려둔 크기.
- `heapUsed`: V8 힙에서 사용 중인 크기.
- `arrayBuffers`: ArrayBuffer와 Buffer 등의 저장 공간. TypedArray 메모리를 볼 때 함께 확인한다.
- `external`: V8이 관리하는 JavaScript 객체와 연결된 외부 메모리. `arrayBuffers`를 포함하므로 둘을 더하면 중복 계산한다.

`rss`, `heapUsed`, `external`도 독립적인 항목을 합산하는 방식으로 사용하면 안 된다. 전후 차이는 정확한 객체 크기나 실행 중 최고점이 아니다. 채점기가 어떤 방식으로 메모리를 집계하는지도 확인해야 한다. [Node.js 메모리 측정 문서](https://nodejs.org/api/process.html#processmemoryusage)

가능하면 별도 프로세스로 여러 번 실행해 최초 실행을 포함한 시간을 비교한다. 작은 입력에서만 빠른지, 최악의 데이터에서 느려지는지 살피고, 경계에 걸린 풀이는 충분한 여유가 생기도록 개선한다.

## 8. 제출 전 판단 순서

1. 입력 개수, 값의 범위, 테스트케이스 전체 크기를 구분한다.
2. 최악의 반복 횟수에 반복 내부의 탐색·복사·문자열 연산 비용을 곱한다.
3. 모든 자료구조의 원소 수와 동시 보관 개수를 센다.
4. TypedArray는 바이트 수로 계산하고 일반 배열·객체는 부가 비용을 포함해 측정한다.
5. 입력·출력·큐·임시 배열·런타임 공간을 더해 여유를 확인한다.
6. 입력값과 중간 결과가 자료형의 정확한 표현 범위에 들어가는지 확인한다.
7. 최대 입력으로 검증하고, 부족하면 상태 수·연산량·보관할 정보를 줄인다.
